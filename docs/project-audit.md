# Аудит проекта медицинского центра

Дата аудита: 20.04.2026

Цель проекта: сделать рабочее место оператора для двух медицинских центров, не хуже текущего Excel-процесса, с быстрым поиском, минимумом лишних действий и перспективой стабильной работы на базе от 100 000 клиентов.

## 1. Общая картина

Проект сейчас состоит из трех основных частей:

- `backend` - серверная часть на FastAPI. Здесь должны жить база данных, API, импорт Excel, документы, XML, пользователи, права, аудит и резервное копирование.
- `frontend` - React/Vite-приложение. Это задел под нормальную веб-систему, но пока оно не является главным рабочим интерфейсом.
- `demo` - текущий живой UI-прототип. Именно в нем сейчас согласовывается логика рабочего места оператора, внешний вид, карточки клиента, услуги и карточки врачей.

Дополнительно:

- `assets/templates` - папка с шаблонами документов.
- `storage` и `backend/storage` - служебные папки для хранения сгенерированных или рабочих файлов.
- `docker-compose.yml` - заготовка для PostgreSQL.

Главный вывод: сейчас проект находится между демо-прототипом и началом боевого продукта. Интерфейс уже можно показывать и проверять сценарии, но настоящую многопользовательскую рабочую систему еще нужно собирать вокруг backend + PostgreSQL.

## 2. Что уже работает в demo

`demo` сейчас является самой живой и полезной частью проекта.

Реализовано:

- главный экран оператора;
- быстрый поиск клиентов;
- пустая таблица при пустом поиске;
- выдача до 25 найденных клиентов;
- нумерация пациентов простыми номерами `1`, `2`, `3`;
- карточка выбранного клиента;
- добавление клиента;
- изменение клиента;
- автоформатирование дат в форме клиента;
- выбор услуг при добавлении/редактировании клиента;
- справочник услуг;
- группировка услуг;
- добавление и редактирование услуг в demo;
- создание обращения по клиенту;
- активное обращение клиента;
- привязка услуг к обращению;
- сумма обращения;
- комментарий к обращению;
- сохранение изменений demo в браузере через `localStorage`;
- карточки врачей;
- сохранение осмотра врача в память demo;
- привязка осмотра врача к активному обращению;
- демо-просмотр медицинской справки;
- демо-просмотр водительской справки;
- демо-просмотр XML;
- страница шаблонов/врачей с кнопками открытия форм.

Важно: сохранение в `demo` сейчас локальное, в браузере. Это удобно для показа и тестирования, но это не настоящая база данных.

## 4. Что уже есть в backend

Backend запускается на FastAPI и уже имеет основу нормальной системы.

Есть модели:

- роли;
- центры;
- клиенты;
- обращения;

- категории услуг;
- услуги в обращении;
- оплаты;
- повторы;
- шаблоны документов;
- документы клиента;
- аудит;
- партии импорта.

Есть API-разделы:

- авторизация;
- dashboard;
- клиенты;
- обращения;
- услуги;
- документы;
- повторы;
- оплаты;
- услуги внутри обращения;
- документы клиента;
- health-check.

Есть начальная логика:

- создание таблиц при старте;
- добавление поля `patient_number`, если его нет;
- заполнение номеров пациентов;
- индексы для номеров пациентов;
- служебные поля для импорта старой базы;
- seed справочников;
- генерация документов из шаблонов;
- скачивание сгенерированных документов.

Ограничения backend на сейчас:

- авторизация пока демо-уровня, без нормальных JWT/сессий;
- нет полноценной системы прав;
- нет полноценного удаления с аудитом и email-уведомлением;
- нет API для врачебных осмотров;
- не все сущности имеют update/delete;
- основная рабочая база пока SQLite, PostgreSQL только подготовлен через `docker-compose.yml`;
- нет готового production-механизма резервного копирования;
- импорт Excel/MDB есть как заготовка, но требует отдельной проверки на актуальной базе.

Вывод: frontend пока лучше считать заготовкой, а не финальной рабочей системой.

## 6. Данные и хранение

Сейчас есть несколько уровней данных:

- `demo/legacy-data.js` - текущие клиентские данные для demo. Этот файл нельзя случайно перезаписывать и нельзя бездумно отправлять наружу.
- `localStorage` браузера - сохраняет изменения demo на конкретном компьютере и в конкретном браузере.
- `backend/medcenters.db` - локальная SQLite-база backend.
- PostgreSQL в `docker-compose.yml` - будущая боевая база.

Главное: сейчас demo и backend живут не как единая боевая система. Для настоящего продукта нужно перенести рабочую логику demo в backend/frontend и хранить данные в PostgreSQL.

## 7. Что не трогать без необходимости

До отдельного решения лучше не трогать:

- `demo/legacy-data.js` - там клиентские данные;
- реальные шаблоны документов в `assets/templates`, если задача не про их подключение;
- сгенерированные документы в `backend/storage/generated`;
- untracked-файлы, которые могли быть добавлены пользователем вручную;
- историю git и чужие изменения.

## 8. Главные риски

Технические риски:

- demo сохраняет данные только локально в браузере;
- при работе с нескольких компьютеров изменения demo не синхронизируются;
- врачебные осмотры пока не сохраняются в backend;
- backend еще не полностью закрывает реальные рабочие сценарии;
- frontend еще не является рабочим местом оператора;
- нет полноценной авторизации, ролей и аудита;
- нет production-бэкапов;
- PostgreSQL еще не стал основной рабочей базой;
- часть текстов в проекте повреждена кодировкой.

Бизнес-риск:

- клиент может принять demo за готовую систему. Поэтому при показе нужно честно говорить: "Интерфейс и сценарий согласованы, дальше переносим это в боевую базу и многопользовательский режим".

## 9. Правильный порядок сборки боевой версии

Рекомендуемый порядок:

1. Зафиксировать модель данных PostgreSQL.
2. Перенести клиентов и быстрый поиск в backend.
3. Сделать быстрый API поиска с лимитом 25-50 записей.
4. Подключить главный экран оператора к backend.
5. Сделать создание и изменение клиента через backend.
6. Сделать антидубли по документам, телефону, СНИЛС, полису и дате рождения.
7. Перенести услуги в backend.
8. Сделать обращение как обязательную рабочую сущность: клиент, дата, центр, услуги, сумма, комментарий.
9. Привязать врачебные осмотры к обращению.
10. Перенести карточки врачей из demo в нормальную систему.
11. Подключить реальную генерацию документов к обращению.
12. Подключить XML к обращению и услугам.
13. Сделать автонумерацию бланков для нужных услуг.
14. Сделать пользователей и роли: админ, оператор, касса, врач.
15. Сделать аудит и email-уведомления при удалении.
16. Сделать повторы.
17. Сделать импорт актуальной базы.
18. Настроить резервное копирование.
19. Провести нагрузочную проверку на 100 000 клиентов.

## 10. Что важно для скорости на 100 000 клиентов

Нужно заложить сразу:

- PostgreSQL;
- индексы по ФИО, дате рождения, телефону, документам, номеру пациента;
- поиск только через backend;
- лимит выдачи 25-50 строк;
- debounce поиска 200-300 мс;
- не загружать всех клиентов на страницу;
- не хранить 100 000 клиентов в JS-файле;
- отдельная генерация документов, не связанная с поиском;
- кеширование справочников услуг и врачей;
- аккуратная пагинация или виртуализация таблиц.

Главное правило: система должна быть рабочим местом оператора, а не сайтом с разделами.

## 11. Как показывать клиенту сейчас

Правильная формулировка:

"Это интерактивный прототип рабочего места оператора. Здесь уже видно, как будет проходить оформление клиента: поиск, добавление, выбор услуг, обращение, врачи, справки и XML. После утверждения сценария мы переносим это в боевую архитектуру с сервером, базой данных, пользователями, правами и резервным копированием."

Не стоит говорить:

- что это уже финальный продукт;
- что данные уже надежно хранятся в общей базе;
- что можно завтра запускать два центра в работу без backend-доработки;
- что права, аудит и бэкапы уже полностью готовы.

## 12. Ближайший практический шаг

Самый правильный следующий шаг: начать перевод `demo` в боевой контур.

Первый модуль:

- PostgreSQL;
- таблица клиентов;
- быстрый поиск;
- создание клиента;
- изменение клиента;
- антидубли;
- нумерация пациентов;
- подключение главного экрана к backend.

После этого можно переносить услуги и обращения. Это даст первый настоящий рабочий фундамент, на который уже безопасно навешивать документы, XML, врачей и роли.
